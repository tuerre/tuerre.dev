# Migrar un Portfolio de Next.js a Astro: Qué Cambió, Qué Mejoró y Qué Me Dio Problemas

Mi portfolio empezó en Next.js y hoy corre sobre **Astro 5**. No lo migré porque Next.js sea malo, sino porque un portfolio es sobre todo contenido estático con unos pocos componentes interactivos, y Astro está diseñado exactamente para eso.

## Por qué Astro encaja con un portfolio

Astro genera HTML estático por defecto y envía **cero JavaScript** al navegador salvo el de los componentes que le pidas explícitamente. Para un sitio donde importan la velocidad de carga y el SEO, esto es una ventaja clara:

- Menos JavaScript significa mejores Core Web Vitals.
- El HTML llega completo, listo para que Google lo indexe.
- El contenido (blog y páginas) no necesita hidratarse.

## La estrategia: islas de React

No tuve que reescribir mis componentes. Con `@astrojs/react`, los componentes `.tsx` existentes siguen funcionando y se hidratan solo donde se necesita:

```astro
---
import Hero from "../components/sections/Hero";
import GithubActivity from "../components/sections/GithubActivity";
---

<Hero client:load />
<GithubActivity client:visible />
```

- `client:load` hidrata el componente apenas carga la página.
- `client:visible` espera a que el componente entre en pantalla, ideal para secciones más abajo.

## El tema claro y oscuro entre islas

Un problema real: `next-themes` depende de un contexto de React, pero en Astro cada isla es independiente y **no comparten contexto**. La solución fue guardar el tema en la clase `.dark` del DOM y emitir un evento `themechange` que cada isla escucha. Así todas se sincronizan sin un provider compartido.

## Blog con content collections y MDX

Astro trae colecciones de contenido con validación de esquema. Cada artículo es un archivo `.mdx` y el frontmatter se valida con Zod:

```ts
import { defineCollection, z } from "astro:content";
import { glob } from "astro/loaders";

const blogs = defineCollection({
  loader: glob({ pattern: "**/*.mdx", base: "./content/blogs" }),
  schema: z.object({
    title: z.string(),
    slug: z.string(),
    publishedAt: z.string(),
    description: z.string(),
    image: z.string().optional(),
    tags: z.array(z.string()).optional(),
  }),
});
```

Si olvido un campo, el build falla en vez de publicar un artículo roto. Eso es un seguro enorme para el SEO.

## SEO que se puede automatizar

- **Sitemap automático** con `@astrojs/sitemap`.
- **Metadatos por página**: título, descripción, canonical y Open Graph.
- **Imagen Open Graph** por artículo, para que se vea bien al compartir.
- **Rutas estáticas** para cada artículo con `getStaticPaths`.

## Rutas dinámicas sin perder el control

El portfolio todavía tiene un endpoint que necesita servidor: obtiene mis contribuciones de GitHub y las guarda en caché con Upstash Redis. Astro permite mezclar páginas estáticas con rutas bajo demanda mediante el adaptador de Vercel, así que solo ese endpoint se ejecuta en servidor.

## Lo que me dio problemas

1. **Contexto de React entre islas**: ya mencionado, hay que repensar el estado compartido.
2. **Directivas `client:*` olvidadas**: un componente interactivo sin directiva se renderiza pero no responde a clics.
3. **Rutas con trailing slash en Vercel**: lo conté en [este artículo](/blog/error-500-vercel-rutas-trailing-slash).

## ¿Vale la pena?

Para un portfolio o un blog, sí. Para una aplicación con mucha interacción y estado global, Next.js sigue siendo una opción excelente. La clave es elegir la herramienta según el tipo de contenido.
